# 0.14.0 Error monitoring (Sentry), test page, privacy

**Goal:** every error the app already logs reaches Sentry with its context;
a test page fires each kind of error on purpose and exists only where a
server env variable turns it on; the setup sends as little personal data as
the UK and EU rules ask; the README and an ADR say what a real production
launch would still need (privacy notice, consent banner, EU data region).

Sources read (2026-11-06): Sentry's agent skill `skills.sentry.dev/instrument`,
Sentry docs for Next.js (manual setup, options `dataCollection`, data
collected, data storage location, build options `tunnelRoute` and source
maps), Next.js docs via Context7 (`instrumentation.ts` `register` /
`onRequestError`, `instrumentation-client.ts` `onRouterTransitionStart`).
`@sentry/nextjs` 11.11.0 (in v11 the `dataCollection` defaults always apply
and collect a lot, so every category is set explicitly).

## Owner decisions (2026-11-06)

1. **Versions:** Sentry is 0.14.0, the Vercel deploy and E2E on previews move
   to 0.15.0.
2. **Data region:** keep the existing US organisation (`dmitriy-f`, project
   `market-ops-console`) for the demo, send the minimum, and write down that a
   production launch for UK/EU users uses an EU organisation (Frankfurt).
3. **Signals:** errors and tracing (10 % of traces in production, 100 % in
   development). No Session Replay, no feedback widget, no Sentry logs or
   metrics.
4. **Test page:** behind a server variable `ENABLE_SENTRY_TEST_PAGE`, turned
   on **only locally** (`.env.local`). Off, the page and its API answer a
   plain 404, as if they did not exist. On Vercel (preview and production) it
   is never set.
5. **README and ADR:** if this went to production, a cookie / consent banner
   that explains what is stored would be required (UK GDPR, PECR, EU
   ePrivacy); without it the launch breaks the law.

## My calls (say if any is wrong)

- **One place, already there:** `logError` and `logEvent` (`shared/lib`) are
  the only places errors and product events are recorded (about ten call
  sites). Sentry plugs in there, so no call site changes and no new hook:
  - `logError(error, { scope, ...context })` → `Sentry.captureException`
    with tag `scope` and the context as `extra`; `console.error` stays.
    Not sent: expected 4xx `AppError`s (`expose: true`: validation, not
    found) and errors with a `digest` (a server error Next already reported
    through `onRequestError`; the browser only gets a stripped copy). The
    existing "log each error object once" stays.
  - `logEvent(name, data)` → a Sentry breadcrumb (category `event`), so an
    error shows the product steps before it. Never the question text (as now).
  - **Lint rule:** `@sentry/nextjs` may be imported only in `logError`,
    `logEvent`, the Sentry init files and `next.config.ts`; anywhere else lint
    says "use logError / logEvent". Same pattern as 0.13.1.
- **Off without a DSN:** `NEXT_PUBLIC_SENTRY_DSN` (client env in `env.ts`;
  a DSN is public by design). Not set in unit tests, E2E or CI, so they never
  send events; set in `.env.local` to try it. Not committed.
- **Shared options** in one function `sentryOptions()`
  (`src/shared/config/sentry.ts`): DSN, `enabled`, `environment`
  (`NODE_ENV` now; `VERCEL_ENV` in 0.15.0), `tracesSampleRate`, and
  `dataCollection`:
  - `userInfo: false` (no IP address, no user id),
  - `cookies: false`, `httpHeaders: false` (no `X-Forwarded-For`, no
    `Accept-Language`), `httpBodies: []` (no request or response bodies:
    the chat question is a body),
  - `urlQueryParams: true` (the dashboard state: market ids, period, mode;
    no personal data, and it is what a bug report needs),
  - `stackFrameVariables: false`, `genAI` / `mcp` off.
  The three `Sentry.init` files (client, server, edge) call it, as the docs
  lay them out: `instrumentation-client.ts`, `sentry.server.config.ts`,
  `sentry.edge.config.ts`, `instrumentation.ts` with `register` and
  `onRequestError = Sentry.captureRequestError`, at the root next to `app/`.
- **Tunnel `/monitoring`** (`tunnelRoute`): the browser sends events to our
  server, which forwards them. Ad blockers do not drop them, and the
  visitor's browser never talks to sentry.io (Sentry sees the server, not the
  visitor's IP; a future CSP needs no Sentry host). Cost: the server forwards
  each event. The proxy matcher skips `monitoring` (the docs require it with
  Turbopack).
- **Source maps:** `withSentryConfig` uploads them only when
  `SENTRY_AUTH_TOKEN` is set (server env, build only); without it the build
  skips the upload quietly. The token goes into Vercel in 0.15.0. Maps are
  hidden from the browser and deleted after upload (v11 default).
- **Test page** `/[locale]/sentry-test` (`src/pages/sentry-test`, text in
  en/de/ru like everything else), checked on each request (`connection()`,
  so a build cannot freeze the answer). Buttons, each says what it fires and
  where to see it:
  1. client error in a click handler (uncaught, the SDK's global handler);
  2. client render error (a component throws, the route's error page, `logError`);
  3. a handled error through `logError` (the page stays);
  4. an unhandled promise rejection;
  5. API error: `GET /api/v1/sentry-test` throws inside `withErrorHandling`
     (500, `logError` on the server); 404 when the page is off;
  6. server render error: `/[locale]/sentry-test/server` throws in a Server
     Component (`onRequestError`, then the 500 page with the error ID);
  7. a traced span (`Sentry.startSpan` through a small helper in `shared/lib`,
     not a direct import) to check tracing.
- **No experimental Next.js feature** (ADR 0018 rule): `instrumentation.ts`,
  `instrumentation-client.ts` and `onRequestError` are stable in Next 16.
- **Privacy text** (README section "Error monitoring and privacy", ADR 0019):
  what Sentry gets and does not get; what the app stores on the device
  (`NEXT_LOCALE` cookie, the alert rules cookie, theme / mode / currency /
  view in `localStorage`, the chat in `sessionStorage`; Sentry adds no
  cookie without Replay); and what production needs: a privacy notice
  (Art. 13), Sentry's DPA (Art. 28), an EU organisation or the transfer
  safeguards (Art. 44–46: SCCs / UK IDTA addendum / Data Privacy Framework),
  a retention period set in Sentry, and a consent banner listing what is
  stored and why, with non-essential tracking off until accepted (PECR
  reg. 6; ePrivacy Art. 5(3)). Not legal advice; a production launch gets a
  DPO or lawyer's review.

## Audit: what can fail and is it seen (2026-11-06, owner asked)

Every `catch`, error callback and risky browser API in `src/`, `app/` and
`proxy.ts` was read.

Already logged, reaches Sentry through `logError` once it is wired:
- every failed query and mutation (`QueryCache` / `MutationCache`, user
  aborts skipped); every API route (`withErrorHandling`: 5xx and unexpected
  errors, 4xx answered without a log); the chat stream on both sides (server
  phase `stream`; client: invalid event, server `error` event, `done` with
  kind `error`, stream closed without `done`, transport); widget and route
  error boundaries (`WidgetBoundary`, `error.tsx`, `global-error.tsx`;
  a chart chunk that fails to load lands in its widget boundary); the Excel
  and CSV export.

Covered by the SDK itself, no code: uncaught errors and unhandled rejections
in the browser; Server Component, route handler and proxy errors
(`onRequestError`); page loads, navigations and `fetch` calls as traces.

Gaps, fixed in this release:
1. **Silent data loss, now a warning** (new `logWarning(message, context)`
   next to `logError`: `console.warn` + a Sentry message at level
   `warning`):
   - the alert rules cookie cannot be read (`decodeRules` returns null, the
     user's rules are gone and the next write replaces them), server;
   - a stored chat exists but fails the schema (a format change after a
     deploy would wipe every open conversation without a trace), client;
   - the chat cannot be saved because storage is full (`QuotaExceededError`;
     a blocked storage in a private window stays silent: expected).
2. **Not everything failed is a bug** (one function decides, `reportLevel`,
   tested): expected answers the user caused are not sent as errors (client
   `HttpError` with `duplicate_name`, `too_many`, `not_found`; they stay a
   breadcrumb); offline and timeouts (`NetworkError`, `TimeoutError`) go as
   `warning`; a 400 from our own form is a bug and goes as `error`.
3. **Context on every event**, no personal data: tags `locale`, `mode`,
   `currency`, `section` (phone tab), and `release` = `market-ops-console@`
   + the version in `package.json`, so an issue names the release. Set once in
   the app providers through a helper (`setMonitoringContext`), not per call.
4. **What to watch, as spans** (through a `traceSpan` helper): the chat answer
   (`chat.answer`: time to the first token and to `done`, `kind`,
   `confidence`; never the question) and the Excel export (`export.xlsx`:
   time, rows). These are the slow paths a user feels.

5. **The assistant cites something the dataset does not have** (a citation
   that resolves to "Not in the dataset"): today only the UI says so. Now a
   `warning` with the citation's ids and period (`scope: 'chat'`), once per
   answer: it means the AI or the data is wrong.
6. **A broken link is repaired silently** (`useDashboard` replaces unknown
   market, region, product, period, mode or metric in the URL): now a
   breadcrumb `url_fixed` with the names of the repaired params, so an error
   right after shows the link was bad. Not an issue of its own (a hand-edited
   or old link is normal). Same for a 404: a breadcrumb `not_found`, no issue.

Checked, nothing to add:
- a click handler that throws, or an async one that rejects: the SDK's global
  handlers catch both (test page buttons 1 and 4 prove it);
- the alert rule switches, edits and deletes: failed writes go through
  `MutationCache` (logged) and the rollback toast;
- the export: building the CSV or the workbook, loading ExcelJS and starting
  the download are inside one `try` that logs and shows a toast. A download
  the browser itself blocks cannot be seen from the page (the link click does
  not fail);
- an abstain or a low-confidence answer is not a failure (it is the
  contract); only `kind: error` is logged, as now.

Left as they are, on purpose: the inline head scripts (theme, mode, tab,
panel) swallow a blocked `localStorage` and run before Sentry starts;
`stored-value` and the clipboard (blocked storage or clipboard is the
user's setting, the UI already says so); React's recoverable hydration
errors (Next gives no hook outside the console; noted in the ADR).

## Risks

- About 30–40 KB more client JS (gzip) for the SDK with tracing.
- A user offline or with a timeout produces client errors that are reported
  (useful, may be noisy); filter later by scope if it is.
- The tunnel adds server work per event; on Vercel it counts as function
  invocations.
- The organisation is in the US: for the demo, events from UK/EU visitors
  are stored in Iowa. They carry no IP, no headers, no bodies, no user id.
- Without the token (until 0.15.0) production stack traces are minified.

## Found during the release

- **`withSentryConfig` turns on an experimental Next.js flag** (`clientTraceMetadata`) with no option to stop it: the build printed "Experiments (use with caution)". It is removed from the final config (ADR 0018 rule); page-load and server traces arrive as two traces.
- **The default tunnel (rewrite mode) forwards every request header to Sentry**, the visitor's IP in `X-Forwarded-For` included, and printed `MaxListenersExceededWarning` on each event (checked: only tunnel requests). Switched to handler mode (`app/sentry-tunnel/route.ts`, body only); the warning is gone, a foreign DSN gets 403, garbage 400. The path is `/sentry-tunnel` (was `/monitoring` in the plan).
- **`MonitoringTags` read the URL outside Suspense** and broke the static dashboard build: wrapped in `Suspense`.
- **`logWarning` takes a stable code** (`chat_dropped`), not a sentence: the i18n lint rule flags sentences in `.ts`, and Sentry groups issues by the message, so a code is better anyway.
- **The two `no-restricted-imports` rules are one** (the dataset one from 0.13.1 and Sentry's): a second block for the same files would have replaced the first. Probed: a widget importing Sentry or the raw dataset query fails, the allowed files pass.
- The Excel span has no row count (only time).
- **Checked in the browser** (production build on :3100 with the DSN passed in the command and the test page on, ru and de): every button; events go to `/sentry-tunnel` with 200, the browser never calls sentry.io; an event carries the tags (`locale`, `mode`, `currency`, `section`), no `user`, a `request` with the URL only; the server render error shows the 500 page with its error ID; the API answers 500 and logs on the server. **Not checked by me: that the events appear in Sentry** (no Sentry access here): owner check.
- **Owner check (2026-11-06):** the tunnel answered 500 "Tunnel route requires Sentry server SDK initialized with a DSN" (the default handler asks the server SDK for the allowed DSN): the DSN is now passed explicitly from env, a 404 without one; tests for 404 and a foreign DSN (403). The API and trace buttons got a loading state (spinner, "Sending…", `aria-busy`, a second click ignored); checked in the browser. The IDE showed `no-unsafe-assignment` on `env.SENTRY_ORG` in `next.config.ts`; `pnpm lint` and `eslint next.config.ts` report nothing, so it is the editor's stale ESLint/TypeScript server.
- **Security review (automated, 2026-11-06): the SDK's handler mode still forwards the visitor's IP** (`X-Sentry-Forwarded-For` from `X-Forwarded-For` / `X-Vercel-Forwarded-For` / `CF-Connecting-IP`) and the user agent, client hints, origin and referer, despite its docs. Confirmed in `@sentry/core` (`forwardHeaders`). The route now hands the SDK a new request with the body and its length only (bodies over 1 MiB: 413); a test with a mocked `fetch` checks that only `content-type` leaves. My earlier "only the body goes on" in ADR 0019 was wrong; corrected.

## Independent review (2026-11-06)

Checked on the wire (a local capture server): no IP, user agent, cookies or bodies in browser or server events; the question text nowhere; no double reports for render errors; the test page dynamic and 404 when closed; no experimental flag in the built config. No critical findings.

Fixed:
- **A server 5xx was reported twice** (the server's exception and the browser's `HttpError` copy): `reportLevel` skips a 5xx with our own code (`internal`, `data_integrity`); a 5xx without one (a gateway) is still an error. The chat stream's mid-stream overlap stays (written down in ADR 0019).
- **The demo switch made an issue on every use**: `simulated` is expected.
- **An unreadable alerts cookie warned on every load** (and a crafted one could burn the quota): GET clears it; a dropped stored chat is removed. Tests for both.
- **Lint**: the merged block had taken tests out of the ADR 0017 dataset rule (a loosening): tests are under it again, only the Sentry pattern is lifted for them; root files are checked; a dynamic `import('@sentry/…')` is caught. Probed.
- **The test page showed it exists**: its messages are not sent with other pages, its routes are out of Sentry's route map, the link does not prefetch.
- **The tunnel path had "sentry" in it**: `/monitoring` (rewritten to the handler). Ad-block lists not checked.
- Docs: the edge comment (no edge runtime in use), the privacy write-up (fetch and console breadcrumbs, locale and time zone, sessions, no browser/OS breakdown), the E2E DSN, the duplicate ADR sentence. Two `as` casts in tests removed.
- Tests added: `next.config.test.ts` (no experimental key; probed), `src/shared/config/sentry.server.test.ts` (a real server SDK with our options drops IP, cookies and headers from a request error; probed with collection on: it catches the IP), the tunnel's no-body 400, the alerts cookie and chat drop, and `e2e/sentry.spec.ts` (four scenarios on the real browser SDK; the demo-switch one probed).

Recorded, not fixed: `loadChat` warns during render (twice in dev Strict Mode); Sentry's `bundleSizeOptimizations` (webpack-only options; this build is Turbopack); the export span's error status untested; `MonitoringTags` through `Providers` untested.
