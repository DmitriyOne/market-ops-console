# 0019. Error monitoring with Sentry, the test page, and personal data

**Context.** Until 0.13.0 every error went to `console.error` through `logError`, whose comment said a reporting service would plug in there. The owner asked (2026-11-06) for Sentry, a page that fires each kind of error on purpose and cannot be reached in production, a setup that respects the UK and EU rules on personal data (IP addresses included), and a written note on what a real launch would still need: a consent banner above all. Sources: Sentry's agent skill (`skills.sentry.dev/instrument`), Sentry's Next.js docs (manual setup, `dataCollection`, data collected, data storage location, `tunnelRoute` and its handler mode), Next.js docs via Context7 (`instrumentation.ts`, `onRequestError`, `instrumentation-client.ts`). `@sentry/nextjs` 11.11.

**Decision.**
- **Setup as the docs lay it out:** `instrumentation-client.ts` (browser, plus `onRouterTransitionStart` for navigations), `sentry.server.config.ts` and `sentry.edge.config.ts` loaded by `instrumentation.ts` (`register`), and `onRequestError = Sentry.captureRequestError` for Server Components, route handlers and the proxy. Nothing runs on edge today (the Next 16 proxy runs on Node.js), so the edge config is there for a future edge route. All three `init`s take one `sentryOptions()` (`shared/config/sentry.ts`), so they cannot drift. `instrumentation.ts` reads `process.env.NEXT_RUNTIME` directly, the one exception to "env through `env.ts`": Next replaces it at build time so each runtime keeps only its own config.
- **Off without a DSN, and off on this machine unless asked** (owner, 2026-11-06, after local errors showed up in Sentry). `NEXT_PUBLIC_SENTRY_DSN` (client env; a DSN is public by design). Sentry sends from a Vercel deployment, with `NEXT_PUBLIC_VERCEL_ENV` (set by Vercel) as the environment: `production` or `preview`. On this machine (`next dev`, or `pnpm build` + `next start`) the DSN in `.env.local` alone sends nothing; `NEXT_PUBLIC_SENTRY_LOCAL=true` sends, as environment `local`, never `production` (it was `NODE_ENV` before, so a local build and a preview both reported as production, and every console line of `next dev` went to Sentry Logs). Unit tests never send events. E2E runs Sentry on (`NEXT_PUBLIC_SENTRY_LOCAL=true`), as in production, with a DSN on a local port nothing listens on (`e2e/sentry-dsn.ts`); the fixtures catch every browser envelope at the tunnel, so nothing leaves the machine and `e2e/sentry.spec.ts` reads what the real SDK sends. Signals: errors, and traces at 10 % in production, 100 % in development (owner). **Sentry Logs** (owner, 2026-11-06, after the first setup): every `console.log`, `console.warn` and `console.error`, ours and libraries', in the browser and on the server, through `consoleLoggingIntegration` as Sentry's instructions set it up (owner chose this over sending only our helpers' logs). So **anything printed to the console reaches Sentry**: no personal data and never the question text in a console call (CLAUDE.md, AGENTS.md); `console.info` (what `logEvent` prints) is not among the levels, events stay breadcrumbs. No Session Replay, no feedback widget, no metrics.
- **Personal data: as little as possible** (owner: UK/EU). `dataCollection`: no user info (no IP, no user id), no cookies, no headers (no `X-Forwarded-For`, no `Accept-Language`), no request or response bodies (a chat question is a body), no local variables; query parameters kept (the dashboard state: market ids, period, mode; no personal data, and a bug report needs them). The browser sends events to our own path `/monitoring` (neutral: filter lists block paths with "sentry"; whether a given list blocks `/monitoring` is not verified), which Sentry rewrites to `app/sentry-tunnel/route.ts`, so the browser never talks to sentry.io. The route passes Sentry a fresh request with **the event body and its length only**: the SDK's own handler (`@sentry/nextjs/tunnel`, "handler mode") forwards the visitor's IP as `X-Sentry-Forwarded-For` plus the user agent, client hints, origin and referer, although its docs say "only the event payload" (found by an automated security review and in the SDK source; a test checks that only `content-type` leaves). The default rewrite mode is worse: it forwards every request header, and printed `MaxListenersExceededWarning` on each event. The allowed DSN is passed from env (another DSN gets 403; by default the handler asks the server SDK and answers 500 when that client is not up), bodies over 1 MiB get 413 (counted as the bytes arrive, so a chunked body with no length cannot pass), and without a DSN the route is a 404. Defence in depth for production: turn on "Prevent Storing of IP Addresses" in the Sentry project's security settings.
- **One place decides what is sent.** `logError` (console + `captureException` with tags `scope`, `code` and the context as `extra`), `logWarning` (console + a `warning` message; a stable snake_case code such as `chat_dropped`, details in the context), `logEvent` (console + a breadcrumb), and in `shared/lib/monitoring` `reportLevel`, `setMonitoringContext`, `startMonitoredSpan`, `traceSpan`. `reportLevel` keeps as a breadcrumb only: an expected 4xx `AppError`; a client `HttpError` the user caused (`duplicate_name`, `too_many`, `not_found`, and `simulated` from the demo switch); a 5xx with our own server-fault code (`internal`, `data_integrity`: the server reported the real exception, the browser's copy has no cause; independent review); a user abort; and an error with a `digest` (a server error Next already reported; the browser holds a stripped copy). Offline, timeouts and a `ChunkLoadError` (a stale tab after a deploy) are `warning`; everything else is `error`, a 400 from our own form and a 5xx the server never saw (a gateway, a crashed function) included. The chat stream is the one known overlap: a real exception mid-stream is logged by the server (`phase: 'stream'`) and its `error` event by the browser; the browser cannot tell it from the `error` fixture, so both stay. Lint allows `@sentry/*` only in those helpers, `shared/config/sentry.ts`, the Sentry start-up files, `next.config.ts` and the tunnel route: `no-restricted-imports` (root files included; tests may mock the SDK) and a `no-restricted-syntax` selector for a dynamic `import('@sentry/…')`.
- **What was added after a read of every `catch` and error callback** (owner asked): warnings when data is lost without an exception (the alert rules cookie unreadable: warned once and cleared, so a broken or crafted cookie cannot repeat it on every load; a stored chat that fails its schema: warned once and removed; the chat not saved because storage is full; a blocked storage stays silent: the user's setting); a warning when an answer cites what the dataset lacks (`unknown_citation`); breadcrumbs for a repaired link (`url_fixed`, the param names) and a 404 (`not_found`); tags on every event: `locale`, `mode`, `currency`, `section` (`MonitoringTags` in the providers); spans for the two slow paths a user feels: `chat.answer` (time to the first token and to the end, kind, confidence, citation count; never the question) and `export.xlsx`. Already logged before and now reported: failed queries and mutations, route handlers, the chat stream, error boundaries, the export. The SDK itself catches uncaught errors and unhandled rejections in the browser.
- **Release** `market-ops-console@<version>` from `package.json` (`withSentryConfig` `release.name`). **Source maps** are uploaded (and deleted from the build) only when `SENTRY_AUTH_TOKEN` is set; `SENTRY_ORG` and `SENTRY_PROJECT` come from env too (owner), and a token without them stops the build. Until the token is set (0.15.0, in Vercel) production stack traces stay minified.
- **No experimental Next.js feature** (ADR 0018): `withSentryConfig` always turns on `experimental.clientTraceMetadata` (it links the browser's page-load trace to the server render) and has no option to stop it, so `next.config.ts` removes it from the final config. Page-load and server traces arrive as two traces; errors and other traces are unaffected.
- **Test page** `/[locale]/sentry-test` (`src/pages/sentry-test`, en/de/ru): client error in a click handler, render error, handled error, unhandled rejection, warning, API error (`/api/v1/sentry-test`, 500 through `withErrorHandling`), server render error (`/[locale]/sentry-test/server`, then the 500 page with the error ID), and a 300 ms trace. The two that wait (the API, the trace) show a spinner and "Sending…" and ignore a second click, as Export does (`aria-busy`, not disabled, so focus stays). All three routes check the server variable `ENABLE_SENTRY_TEST_PAGE` on each request (`connection()`, so a build cannot freeze the answer) and answer a plain 404 when it is off. It is set **only locally** in `.env.local` (owner); never on Vercel. E2E checks the 404s. Its texts are not sent with other pages (the layout leaves the `sentryTest` messages out; the page passes them to its own provider) and its routes are left out of the route map Sentry ships to browsers (`routeManifestInjection`), so production pages do not even reveal that it exists. Exception: the page calls the test API itself (a test tool, not product logic in `src/pages`).

**Personal data, and what production needs** (owner: README and here). Not legal advice; a launch gets a DPO's or lawyer's review.
- What the app keeps on the device: the `NEXT_LOCALE` cookie (language), the `mo-alerts` cookie (alert rules, the mock API's store), `localStorage` (theme, map or tiles, chart or table per widget, the collapsed assistant), `sessionStorage` (the chat, until the tab closes). Sentry without Replay sets no cookie.
- What Sentry gets: the error, its stack, the page URL with its query, the release, the environment, the tags above, the browser's language and time zone, and breadcrumbs: clicks (by CSS path), navigations, `fetch` calls (method, URL, status; no bodies), console lines (so the context `logError` prints: query keys, a component stack) and the product events above; **Sentry Logs**: every `console.log` / `warn` / `error` line, ours and libraries'; release-health sessions (one per page view, no user id or IP); on the server, the request's method, URL and query only. Not: IP, user id, cookies, headers (so no browser or OS breakdown: no user agent is sent; `httpHeaders: { request: { allow: ['user-agent'] } }` would bring it back), bodies, the question text. Checked on the wire by the independent review and by tests (`e2e/sentry.spec.ts`, `src/shared/config/sentry.server.test.ts`).
- **The organisation is in the US** (`ingest.us.sentry.io`, data stored in Iowa) and kept for the demo (owner). For UK/EU users that is a transfer to a third country (UK GDPR / GDPR Art. 44–46).
- **A production launch for UK/EU users needs:** a Sentry organisation in the EU region (Frankfurt; the region of an existing organisation cannot change), or the transfer safeguards (Sentry's DPA with SCCs, the UK addendum, the EU-US Data Privacy Framework); Sentry's DPA in place (Art. 28); a privacy notice that names Sentry, the purpose (finding and fixing faults), the lawful basis (legitimate interests, Art. 6(1)(f), with the balancing test written down) and the retention (set in Sentry's data settings) (Art. 13); and **a cookie / consent banner** that says what is stored on the device and why, with anything not strictly necessary off until the user agrees (PECR reg. 6 in the UK, ePrivacy Art. 5(3) in the EU). Launching without it breaks the law. Turning on Replay would make consent unavoidable.

**Exceptions.** `process.env.NEXT_RUNTIME` in `instrumentation.ts` (above). The `clientTraceMetadata` removal overrides what `withSentryConfig` writes; `next.config.test.ts` fails if any experimental key is set. The test page fetches in `src/pages` (above). `loadChat` runs during render, so in development's Strict Mode a dropped chat can warn twice (once in production).

**Considered.** Sentry's wizard (interactive, and it writes its own example page and files we would rewrite). Rewrite-mode tunnel (forwards the visitor's headers; see above). No tunnel (the browser talks to sentry.io directly: its IP goes to Sentry and ad blockers drop events). Session Replay (more JavaScript and personal data, consent required). Logs through our helpers only (`Sentry.logger` in `logError` / `logWarning` / `logEvent`: nothing a library or a stray debug line prints; owner chose the whole console instead). Keeping `clientTraceMetadata` (an experimental flag in production, against the owner's rule). An EU organisation now (owner: US for the demo, written down for production).

**Consequences.** New code reports through `logError` / `logWarning` / `logEvent` and the monitoring helpers; lint stops a direct Sentry import. A new kind of expected failure goes into `reportLevel`. The test page needs the variable, a DSN and `NEXT_PUBLIC_SENTRY_LOCAL=true` in `.env.local`. 0.15.0 adds `SENTRY_AUTH_TOKEN`, `SENTRY_ORG`, `SENTRY_PROJECT` and the DSN in Vercel, and the environment from `VERCEL_ENV`.
